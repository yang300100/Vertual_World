# 世界内核架构

> 本文描述当前已实现架构。已经确认但尚未实现的目标设计位于 `docs/design/README.md`。

## 权威状态

SQLite 是世界事实的唯一来源。第三方模型、未来表现层和人物主观记忆都不能覆盖客观状态。当前数据库开启外键、WAL 与 `busy_timeout`，适合单服务器、单写入推进器的第一阶段。

## 推进边界

世界运行已拆分为状态心跳和模型裁判。

### 状态心跳

- worker每现实60秒唤醒一次。
- 按实际现实时间差乘以运行时 `time_scale` 推进世界时钟。
- 默认 `time_scale=1.0`，0表示暂停。
- 人物饱食度与精力使用余量累计，1分钟的小数变化不会因整数存储而丢失。饱食度范围为0至100，100最舒适，随世界时间下降。
- 每次心跳写入 `world_heartbeats`；实际整数状态变化写入 `character_state_updates`。
- API和worker启动时重置现实时间基准，因此服务器离线期间不补算。

### 运行时调速

- 调速先按旧比例结算从上次心跳到生效时刻的世界时间和人物连续状态。
- 结算、修改比例和写调速事件位于同一个SQLite事务中，只增加一次 `world.version` 状态修订号。
- `clock_revision` 独立记录时钟配置或心跳修订；它不是软件发布版本。
- 重复设置当前比例返回无操作，不写事件、不增加状态修订号，也不移动心跳基准。
- 若旧比例结算跨过00:00或12:00裁判点，调速事务提交后可继续触发一次独立模型裁判；裁判造成的状态修订不属于调速重复计数。

### 模型裁判

固定世界时间裁判点为00:00和12:00。一次心跳跨过多个裁判点时只合并裁判一次。裁判分为三个阶段：

1. 在只读连接中读取带版本号的世界快照。
2. 在数据库锁外选择活跃人物并产生结构化动作。
3. 开启 `BEGIN IMMEDIATE` 写事务，重新检查版本，校验动作并一次性结算；裁判不推进世界时间。

如果版本已经变化，本轮放弃旧决策并返回冲突，不会把它标记为世界故障。

主视角介入使用 `player_intervention` 即时局部裁判，只选择相关人物，并记录介入时间，但不重置下一全局裁判点。

当前裁判已经实现“人物批量提案 + 本地规则门禁 + 事务提交”。只有规则无法判断时才启用的第二阶段社会冲突模型裁判尚未实现；当前资源冲突按活跃人物顺序逐个使用最新状态校验。

## 决策器边界

外部推理不占用世界写事务；社会交互提交前重新核对快照版本。
记忆整理通过持久化 `memory_jobs` 交给 worker 低优先级处理，保留重试与领取租约。
物品规则及长期事务履约的当前边界见 `docs/design/14-core-completion.md`。

`DecisionProvider` 只接收世界快照和允许详细决策的人物，只返回 `ActionProposal`。当前实现包括 `RuleDecisionProvider` 与 `DeepSeekDecisionProvider`；切换供应商不改变世界引擎和数据库。

DeepSeek适配器把多个活跃人物合并为一次请求，响应必须通过Pydantic结构化校验。网络错误、限流、服务端错误、空响应或无效JSON都会触发有限重试，最终由规则引擎接管当前轮次。世界事件会记录本轮实际使用的是 `deepseek` 还是 `rules`。

DeepSeek适配器启动时还会把配置目录下的Markdown设定分节、分块，并建立进程内BM25索引。知识块分为 `author_hidden`、`guardrail` 和 `character_common`，未标记文档安全地默认为 `author_hidden`。人物决策只检索不含隐藏事实的叙事护栏和普通人物通用知识；作者隐藏真相在构造模型请求之前被排除。知识块保留来源和章节，叙事硬约束始终召回，模型结果还要经过底层禁用术语检查，失败时进入原有规则降级路径。

知识库不是新的世界事实源。它只约束模型提案，不写SQLite、不跳过动作门禁，也不代替未来的观察者知识图。`character_common` 只承载所有普通人物共享的常识，不能存放单个人物的秘密或记忆。当前索引在进程启动时构建；修改知识文档后需要重启API和worker。

模型无法：

- 直接执行SQL或Shell。
- 直接修改人物属性。
- 宣告行动已经成功。
- 读取与本次决策无关的全部私有数据。
- 从提示词中获得API密钥或服务器环境变量。

## 动作门禁

`ActionService` 是所有人物动作的最终入口。它读取事务内的最新事实，验证地点、资源、金钱、精力和目标人物，再执行状态变化。成功或失败都会形成客观事件；成功行动还会形成参与者的主观记忆。

## 运行进程

- `world_engine.api`：仅提供API，不负责定时推进。
- `world_engine.worker`：独立进程，负责自动推进所有运行中的世界。
- `world_engine.clock`：负责心跳、调速、离线暂停和人物连续状态。
- `world_engine.cli`：本地创建、检查和手动推进世界。

Windows本地编排由 `scripts/start_world.ps1` 负责：复用健康API、防止重复worker、隐藏启动进程、写入项目专用PID和运行日志，再打开控制台。`scripts/stop_world.ps1` 只停止可核验为当前项目 `.venv` 的API和worker进程。

## 轻量表现层

`world_engine.web` 是由FastAPI在 `/ui/` 同源托管的静态控制台，使用HTML、CSS和原生JavaScript，不引入Node常驻进程，也不保存第二份世界状态。页面每5秒只读刷新；调速、心跳、裁判和主视角介入只通过现有API执行。

前端读取服务器时间、最后权威心跳、时间比例和 `last_worker_seen_at`，只在worker心跳新鲜时平滑外推世界时钟。worker离线或超过心跳阈值后立即停止外推，人物状态始终只展示数据库真实值。

当前页面仅面向本地环境。公网部署前必须为写接口增加身份认证、权限门禁、CSRF或等价同源保护，并限制管理员操作频率。

管理页将 `world.version` 显示为“状态修订号”，用于并发校验和状态变更追踪，不表示软件发布版本。

## 世界历史日志

`world_events` 客观事件表仍是权威历史。`WorldHistoryLogger` 在轮次提交后把事件派生为中文Markdown、JSONL和逐轮JSON文件。导出采用跨进程目录锁、UTF-8和同目录原子替换，API与worker同时运行时不会交叉写坏日志。

日志同步失败不会回滚已完成的轮次。CLI或API可以再次从SQLite回填，因此日志是可恢复的观察视图，而不是第二份需要人工维护的世界事实。

分钟心跳只同步 `heartbeats.jsonl`、`state_updates.jsonl` 和人物独立状态日志，不重复重建全部世界编年史。裁判和调速等客观事件才更新 `history.md`。

当前人物表和新状态日志统一使用正向 `satiety`。从旧数据库迁移时按 `satiety = 100 - hunger` 转换当前值；既有客观事件和JSONL是不可变历史，不重写其中的旧字段名。

服务器部署时保持API单worker和世界worker单实例。未来若需要横向扩展，应先将SQLite迁移到PostgreSQL，再实现租约与任务队列。
