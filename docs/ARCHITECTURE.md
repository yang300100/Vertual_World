# 世界内核架构

> 本文描述当前已实现架构。已经确认但尚未实现的目标设计位于 `docs/design/README.md`。

## 权威状态

SQLite 是世界事实的唯一来源。第三方模型、未来表现层和人物主观记忆都不能覆盖客观状态。当前数据库开启外键、WAL 与 `busy_timeout`，适合单服务器、单写入推进器的第一阶段。

## 推进边界

世界运行已拆分为状态心跳和模型裁判。

### 状态心跳

- worker每现实60秒唤醒一次。
- 按实际现实时间差乘以运行时 `time_scale` 推进世界时钟。
- 默认 `time_scale=1.0`，0表示暂停。
- 人物饥饿与精力使用余量累计，1分钟的小数变化不会因整数存储而丢失。
- 每次心跳写入 `world_heartbeats`；实际整数状态变化写入 `character_state_updates`。
- API和worker启动时重置现实时间基准，因此服务器离线期间不补算。

### 模型裁判

固定世界时间裁判点为00:00和12:00。一次心跳跨过多个裁判点时只合并裁判一次。裁判分为三个阶段：

1. 在只读连接中读取带版本号的世界快照。
2. 在数据库锁外选择活跃人物并产生结构化动作。
3. 开启 `BEGIN IMMEDIATE` 写事务，重新检查版本，校验动作并一次性结算；裁判不推进世界时间。

如果版本已经变化，本轮放弃旧决策并返回冲突，不会把它标记为世界故障。

主视角介入使用 `player_intervention` 即时局部裁判，只选择相关人物，并记录介入时间，但不重置下一全局裁判点。

当前裁判已经实现“人物批量提案 + 本地规则门禁 + 事务提交”。只有规则无法判断时才启用的第二阶段社会冲突模型裁判尚未实现；当前资源冲突按活跃人物顺序逐个使用最新状态校验。

## 决策器边界

`DecisionProvider` 只接收世界快照和允许详细决策的人物，只返回 `ActionProposal`。当前实现包括 `RuleDecisionProvider` 与 `DeepSeekDecisionProvider`；切换供应商不改变世界引擎和数据库。

DeepSeek适配器把多个活跃人物合并为一次请求，响应必须通过Pydantic结构化校验。网络错误、限流、服务端错误、空响应或无效JSON都会触发有限重试，最终由规则引擎接管当前轮次。世界事件会记录本轮实际使用的是 `deepseek` 还是 `rules`。

模型无法：

- 直接执行SQL或Shell。
- 直接修改人物属性。
- 宣告行动已经成功。
- 读取与本次决策无关的全部私有数据。
- 从提示词中获得API密钥或服务器环境变量。

## 动作门禁

`ActionService` 是所有人物动作的最终入口。它读取事务内的最新事实，验证地点、资源、金钱、精力和目标人物，再执行状态变化。成功或失败都会形成客观事件；成功行动还会形成参与者的主观记忆。

## 运行进程

- `world_engine.api`：仅提供API，不负责定时推进。
- `world_engine.worker`：独立进程，负责自动推进所有运行中的世界。
- `world_engine.clock`：负责心跳、调速、离线暂停和人物连续状态。
- `world_engine.cli`：本地创建、检查和手动推进世界。

## 世界历史日志

`world_events` 客观事件表仍是权威历史。`WorldHistoryLogger` 在轮次提交后把事件派生为中文Markdown、JSONL和逐轮JSON文件。导出采用跨进程目录锁、UTF-8和同目录原子替换，API与worker同时运行时不会交叉写坏日志。

日志同步失败不会回滚已完成的轮次。CLI或API可以再次从SQLite回填，因此日志是可恢复的观察视图，而不是第二份需要人工维护的世界事实。

分钟心跳只同步 `heartbeats.jsonl`、`state_updates.jsonl` 和人物独立状态日志，不重复重建全部世界编年史。裁判和调速等客观事件才更新 `history.md`。

服务器部署时保持API单worker和世界worker单实例。未来若需要横向扩展，应先将SQLite迁移到PostgreSQL，再实现租约与任务队列。
