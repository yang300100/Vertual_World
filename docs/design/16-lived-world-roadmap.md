# 文字生活世界：实施路线与验收记录

确认日期：2026-09-07。目标是让玩家通过文字在同一个世界持续生活，行为有过程，
人物有自己的生活，关系与环境能留下可信的后果。用户已同意分阶段开始实施。

## 总验收：在一个小镇生活七个世界日

玩家寻找住处、获取工作、实际赴工并取得报酬、购买食物、保管物品、与居民建立关系、
约定见面并承担迟到后果。居民可依据共同经历主动联系。玩家离开页面再回来，
物品、位置、计划与工作进度仍一致。上述体验由世界状态与规则支持，不是固定剧情。

本轮文字生活基础版本已通过统一验收，含独立七日生活场景。各阶段的实现范围与未覆盖边界如下；后续扩展不计为已经实现。

## 各能力的实施原则

- 场景文本只能描写实际存在且当前能感知的交互对象；人物说法不自动变成物品或事实。
- 新房间、设施与所有权通过明确的创建/登记流程进入世界，不批量补造真实存档家具。
- 行动分为开始、进行、部分完成、完成、中止；中止保留已经发生的消耗与成果。
- 同一人物不能同时执行互斥的活动；完成只结算一次，重启不能重复发放收益。
- 直接表达明确意图的普通操作直接执行；高影响契约和长期事实仍遵守既有确认流程。
- NPC 的长期目标、近期计划和当前活动独立，日常连续数值用代码推进；模型处理重要选择。
- 关系通过真实行为、共同经历和时间变化，不靠重复寒暄无限刷分。
- 陌生人姓名、秘密、心情和远处消息不作为全知界面直接公开；认知需要来源。
- 场景、对话、随身笔记、约定与当前活动形成连续的文字交互，不要求玩家理解后台字段。
- 远程信笺保持远程视角；物件动作和实际进展不冒充玩家说过的话。
- 现有存档、用户改动和历史原文保留。迁移不重置角色、资金、物品和时钟。

### L1a 使用与实现

场景页新增“在这里停留”，可选择休息或等待以及 1–720 个世界分钟的持续时间。
也支持明确文本：`动作：休息30分钟`、`动作：等待2小时`。不指定时间时休息默认
60 分钟，等待默认 30 分钟。主动停止使用面板的“结束当前活动”。

休息额外每世界小时恢复 5 点精力，零头累计；已有自然恢复和饱食消耗照常执行，
两类恢复分别审计。等待没有额外休息收益。开始不加精力，完成之后不会继续领取
该次活动收益。活动期间不得同时移动、工作或操作物品；等待期间可交谈，休息期间
普通行动拒绝执行。简单攻击立即打断受击者活动；其他伤势恶化和位移由心跳检测。

室外地面物品以地点为容器；只有在地点中心 100 米范围内才在生活面板显示并允许
拾取/放下。较远时仍能查看自己的背包。L1b 已增加独立的室内地面与家具储物空间；
单件物品的独立地面坐标仍未实现，不把整座城镇的物品都当成伸手可及。

新表 `character_life_activities` 保存开始、预计结束、已结算进度、终止原因与来源事件。
部分唯一索引保证每人最多一项进行中活动。`life.py` 提供活动与场景规则，
`life_api.py` 提供接口，`web/life.js` 呈现服务端结算进度。没有新增后台模型调用。

```text
GET  /api/worlds/{world_id}/player/life
GET  /api/worlds/{world_id}/player/life/items/{item_id}
POST /api/worlds/{world_id}/player/life/items/{item_id}
POST /api/worlds/{world_id}/player/life/activities
POST /api/worlds/{world_id}/player/life/activities/{activity_id}/stop
```

## L1b 使用与验收（2026-09-08）

### 操作入口

1. 在“编年者 → 元素注册 → 登记已有室内布局”填写房间、地点、外层房间（可选）、
   所有者与进入权限。可附加一个储物容器和一个座位；接口最多支持十六件命名家具。
2. 提交只产生待审核登记。核对完整的地点、入口、所有者与家具清单后，使用既有
   “确认登记/拒绝”按钮裁决；登记前场景中不出现房间。相同请求键不会重复创建。
3. 玩家走近入口后，在场景页“房间与家具”开门、进入、离开；门支持关上、上锁和解锁。
4. 房间内可坐下、起身，打开储物柜并按数量存取自己的物品。关柜后不显示内部物品，
   离开房间后也不能远程取物。坐下或持续活动中，需要先起身或结束活动才能离开。

### 状态与权限

- 使用 `life_rooms`、`life_fixtures`、`life_room_access` 保存布局、门/柜状态及许可；
  人物通过 `current_room_id`、`current_fixture_id` 保存当前房间与座位。
- 房间支持最多四层嵌套，必须逐层经过入口；不能从室外直接进入内层房间。
- 私人房间仅所有者与获准者能进入。公共房间可进入，但有主人的储物柜仍需使用许可。
  储物容器必须有明确的房间所有者；房间所有权与已有建筑/土地权属不会互相覆盖。
- 所有者可授予或撤回进入及储物使用许可；许可不会转移物品所有权，获准者只能取走
  自己存放的物品。权限撤销后，已经在里面的人仍可解锁开门离开，避免被困。
- 存取遵守数量、品质、堆叠上限、容器格数和背包容量；失败整个事务回滚。
  库存前后状态关联来源事件，所有者始终保留。
- 室内地面使用 `room_ground`，柜内使用 `fixture_storage`，与原有室外地面分开。
  普通拾取/放下也复用房间边界，不能通过旧动作接口越过容器权限。
- 不同房间即使经纬度相同，也不能当面交谈、交换联络信笺、交易或攻击。
  场景人物、对话对象、群聊、行动观察者与场景叙事加入房间过滤；远程信件保持远程渠道。
- 在室内不能直接开始室外移动；房间状态不会被普通心跳的位置归属刷新抹掉。
  已审核布局通过统一元素注册器和目录登记，人物 Agent 不能凭描述创建房产或家具。

## L1c 活动过程与等候推进（2026-09-09）

### 已实现的行为

- 玩家在工作场所开始一小时工作。开始不领工资，精力与饱食成本随已完成比例结算；
  完成才发放既有规则的 9 枚货币，并产生 `work_completed=true` 的工作事件供契约核验。
  开始事件、赴工与未完成活动不充当履约完成证据。NPC 的旧工作策略暂时保留。
- 编年者可在元素注册页提交制作/修理配方，明确已有原料类型、数量、地点、耗时、
  精力成本与成果或修复幅度。经确认后才能使用；人物不能自行定义生产规则。
- 配方支持最多八种原料，页面目前提供一种原料的简化编辑。制作和修理共用同一
  活动事务。修理对象必须是本人持有、符合类别且非满完好度的单件物品。
- 开始时预留真实材料，修理对象也进入预留区，不能在过程中被普通背包操作重复使用。
  产物与修理结果仅在完成时结算。材料不足不留下活动或扣除库存。
- 中止保留已消耗的时间与精力；当前版本在完成节点投入原料，因此中止会将尚未投入的
  原料及修理对象转为可领取物品。不会把中止描述成制作成功。
- 成果及退还物品在原活动地点和房间领取，按真实背包容量转移，满包不会丢失产物。
  领取接口支持部分数量，页面每次领取一份。所有库存变化关联来源事件。
- 活动保存规则快照，刷新或重启后保留同一配方、进度、预留材料和结果；重试领取
  已转走的物品不能再发一份，完成任务也不会重复发薪或重复修理。

### 等候推进

场景页的“等候到下一处变化”只对本人正在进行的活动可用，单次最多推进两个世界小时，
保持原时间比例；世界暂停时，用户仍可明确执行一次手动等候。

推进终点取当前活动结束、下一次世界裁判、本人契约到期、室外附近的已知行程抵达、
身体资源警戒线以及两小时上限中的最早项。战斗中、身体状态需要处理、活动条件已经
变化或世界裁判尚未处理时，不继续跳时。

世界状态版本在同一写事务内复核，请求标识、活动与输入版本一起保存；重复网络请求
读取同一结果，不多推进一次。仍使用统一时钟处理人物状态、移动、建设和契约，
抵达裁判边界后复用已有裁判流程，不把模型推理放在 SQLite 写事务中。

这里保证的是上述明确边界，不代表已经实现天气突变、声响、所有临时邀请与任意
自由文本约定的预测。那些事件需要后续 NPC 日程和感知系统提供结构化触发点。

### 持久化与接口

活动类型扩展为 `rest/wait/work/craft/repair`。`activity_recipes` 保存已审核规则，
`activity_task_details` 保存快照、空间、实际成本与结果，`activity_time_skips` 保存
主动等候的幂等结果。现有生活活动记录在迁移时保留。

```text
GET  /api/worlds/{world_id}/activity-recipes/catalog
POST /api/worlds/{world_id}/activity-recipes
POST /api/worlds/{world_id}/player/life/tasks
POST /api/worlds/{world_id}/player/life/activities/{activity_id}/advance
POST /api/worlds/{world_id}/player/life/outputs/{item_id}/claim
```

源文件为 `activity_tasks.py`、`activity_waiting.py`、`task_api.py` 和 `web/tasks.js`。
制作/修理材料与成果都来自明确规则，不新增常驻模型 Agent。

### 发现并修复的时钟缺陷

旧迁移的 `SELECT id, current_time FROM worlds` 会把 `current_time` 当成 SQLite
当前时间函数，导致有效世界时钟被误认为“只有时分秒”而改写。现改为有表限定的
列引用，并增加有效世界时间经两次初始化保持原样的测试。

原有两项时间修复测试也因同样的查询错误而被误判为环境限制并跳过；已修正查询并
恢复执行。此修复保护今后的初始化，不追溯猜测或改写真实存档已经记录的时间。

## L1 阶段历史边界（后续变化见 L2–L4）

L1a 使用现有地点和物品，L1b 在明确登记后提供室内家具交互。初期休息为原地休息，
不声称玩家拥有床铺、客房或住宿许可。暂不改变 NPC 的旧休息策略。
世界时间由心跳、调速与上述主动等候推进；尚不提供忽略重要事件的一键跨日。
复杂自由文本、室内视线、天气模拟、生产补货与七日生活总验收仍在后续阶段。

## L2–L4 本轮实施记录（2026-09-10，基础版本已验收）

本节描述当前代码；上文 L1 的测试数字和运行状态均为历史版本记录。

- NPC 日常：每世界小时考虑一次生活需要，使用真实背包食物、合法资源或商人现货，
  到本地工作场所开始耗时工作，按已登记配方生产与收货，沿入口回到自有空房休息。
  临近已确认约定时估算旅程并赴约；饥饿、伤势和既有行程可以导致迟到，逾期按契约记录。
  不自动改写约定期限；需要改变约定时仍需重新协商、确认。
- 主动联系：人物根据共同事务、关系与相遇产生有期限的机会，模型可以选择不开口；
  成功文本才投递信件或当面发言。每人每天一个机会、每世界日最多四条成功联系，
  最多三次生成尝试，忙碌不耗重试次数，过时结果和过期机会不投递。
- 文字感知：同房间是硬边界，低声/普通/喊话分别为 3/20/100 米，群聊也遵守音量。
  目击与听闻记录当时观察者；前端旅程、编年和人物关系使用本人所知经历。
  陌生人不公开姓名和私人记忆；交换联络信笺或实际介绍后才得知姓名。
- 连续行动：最多六步，支持明确多行“动作：… / 说话：…”及模型提出的分步草案。
  每步先落库，持续活动未结束时等候，失败停在原步骤，刷新后可恢复同一序列。
  发言仍只由模型回应；生成失败保留之前已完成动作。
- 生计：商品、营养、资源来源/所有者/补给上限和工资资金经元素注册确认生效。
  买卖扣真实库存与双方钱款；旧文本交易也复核已登记价格。工资先预留、完工支付、
  取消退还。未登记工资账户的旧工作场所保留原 9 枚工资兼容规则。
- 住房：已有房间可明确登记日租金，经 NPC 回应、玩家确认后支付并获得限期使用权。
  同一房间不重复出租；租期到期不瞬移住客，房产所有权不变，个人物品按原规则保存。
- 关系/情绪/消息：保留相识、共同经历、尊重与冲突，正面交往收益每对人物间隔六小时；
  情绪有来源及持续时间。公开消息最多传播三跳，每跳可信度乘 0.8，私下内容不传播。
- 长期归属：工作履历、租住经历、个人技能/居住/交往目标与完成通知持久化；
  既有建设和正式世界身份仍经原审核流程进入世界，不用 UI 标签赋予官职或所有权。

### 这轮文字生活版本的明确边界

室内遮挡目前以房间分区表达，不计算三维视线、穿墙声音、声学反射或家具后的遮挡。
日常地点选择限定当前十公里内和本人家乡；还不是完整社会交通和经济均衡模拟。
实体钥匙、非法开锁、逐工序烹饪、食品腐败、自动议价、社会阶级流动和政治模拟不在
本轮已实现能力内。上述能力不能靠 NPC 台词冒充事实。

七日生活场景使用独立测试存档；正式存档不自动补造商店、居民、食物或工资资金。
