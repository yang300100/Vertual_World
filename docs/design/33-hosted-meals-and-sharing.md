# 请客与食物分享

共同用餐可以各自备食，也可以由邀请者明确提出使用自己的两份食物招待这一次相处。邀请不是转交、进食或完成相处，对方可以拒绝；请客不产生欠款、排他权或更进一步的亲密义务。

## 选择和来源

`SharedLifeIntent` 增加 `meal_supply`：默认 `each_own` 表示双方各用一份自有随身食物；`proposer` 只能用于新的 `invite + meal`，表示邀请者提供双方各一份食物。回应已有邀请仍只引用 `moment_id`，不能借接受、拒绝或退出修改供餐条款。没有明确供餐选择时不推断请客；付款、共同预算或未来采购也不等于已经持有食物。

`shared_meal_offers` 保存原邀请与本人供餐承诺。`shared_meal_servings` 保存每位进食者、真实提供者、原食物批次、实际进食批次及结算事件。来源批次可以在进食后消失，因此批次编号按不可变文字留存，不以库存外键抹掉历史。

## 真实结算

- 继续检查同场景、距离、身体、空闲和赴约日程。双方同意后，重新核验两份食物的实际所有权、随身位置、数量、完好状态、营养和保鲜期限。
- 食物选择同时尊重提供者与进食者对原批次的饮食安排，不能借拆分或转交绕开客人的隔离、回避或留存决定。
- 复用 `InventoryService.transfer(..., preserve_identity=True)` 真实转交客人的一份食物，再由 `FoodService.eat()` 以客人本人进食；保留批次、保鲜、物质追踪和真实背包容量规则。主人和客人各吃一份，不在同一份实物上重复计数。
- 活动、转交、双方进食、库存审计、供餐凭据和状态更新置于同一保存点。即便上层捕获异常后继续提交，背包容量等失败也不会留下半次消耗或一方已开始的活动。
- 食物在开始时就实际消耗，经过约定时间才完成相处。中途退出保留供餐与消耗，不凭空退款，不额外增加关系数值。

## 交互与兼容

自然语言解析、NPC 回复、主动联系与信笺共享既有 `SharedLifeIntent`，供餐条款进入双方已知的相处上下文。模型可以提出自己的邀请、独立接受或拒绝，不代替对方同意。人物档案和筹备后相处表单均提供供餐选择，已有邀请显示实际供餐方；玩家接受的原话包含供餐条款。

共同生活页面提交统一使用带请求回执的 `/player/social-choices`。默认空筹备来源与默认各自供餐字段兼容历史回执；新请求重试不重复消费，后续模型失败不撤销玩家已保存的选择。

## 验证与范围

`tests/test_hosted_meals.py` 验证双方轮流请客、接受前无消耗、历史回执、明确条款、资源失效、饮食安排、满背包回滚、筹备衔接、实际时间、长期记忆与物质去向。

共 413 个不同的相关场景通过；补充的两份及三十份物质批次场景确认实际去向为双方身体。真实模型先询问缘由，说明后才由本人提出供餐邀请；玩家接受后食物从三十份减到二十八份，钱包不变，真实经过十五分钟后完成。自然解析区分假设性询问、各自备食与本人请客。浏览器通过页面接受该真实模型邀请，确认供餐条款、完成状态与长期记忆。运行证据保存在 `run/hosted-meals-*.json`、日志及截图中，均使用隔离存档。

正式 API 与后台已启动，健康检查及新鲜心跳通过；页面加载 `20261017-meals1` 版本，无前端脚本错误。正式世界的共同活动数量仍为零，没有代玩家接受请客或消费食物。正式存档备份路径记录在 `run/hosted-meals-verification.json`。

本阶段请客限于邀请者已有的食物。店铺付账、代为购买、家庭资金、任意物品赠与和共同出行仍需各自的明确选择与真实结算，不从一次请客获得后续权限。
