# 订房筹备完成后的分房休息与会合接续

阶段42把阶段41已完成的各自订房筹备，接到阶段40的一份新分房邀请：保留筹备来源和原来各自的房间，重新填写休息时间，并由对方独立决定是否接受。订房完成仍不会自动建立分房安排、移动人物、进屋休息或恢复旅行。

核心、文本、API 和界面接续已实现；42个文件820项回归、独立存档的真实模型完整运行及19项专项审计已通过。正式服务已更新，15项代码与服务交付核验通过，见 `run/lodging-handoff-verification.json`。因浏览器连接不可用，用户明确选择“这次先交付代码与服务验收”；实际浏览器操作与截图未执行，作为后续待补项，不计入本次已通过结果。

## 来源、原站点与本人房间

`SeparateStayIntent` 新增可空的 `source_lodging_plan_id`，仅新邀请 `propose` 可以填写。即使引用已有筹备，仍须显式填写 `journey_id`、`own_room_id`、`other_room_id`、带时区的 `arrival_world_time` 和本次时间条款，来源编号不替代这些字段，也不替代接受。回应仍只引用真实 `stay_id`，不能改来源、房间或时间。没有来源的旧分房路径继续可用。

来源必须属于同一世界和同一对参与者，并且已经真实 `completed`。规则核验其共同完成事件的类型、人物和筹备编号，以及双方分别报告就绪的事件、本人房间映射和时间；单独把数据库状态标成 `completed`，不能作为有效接续依据。

接续必须沿用同一原旅行、同一实际到站、同一停留序号和同一暂停回执。原旅行仍须有效、暂停且处于已到站停留；旧筹备不能套到后来到达的新站点，或已经恢复后再次暂停的新行程状态。提出新邀请时仍须按原分房规则真实会合、保持可接触和可安排状态。

`own` 始终指本次提出者本人。原筹备由玩家提出而本次分房由 NPC 提出时，字段须按真实人物反向映射；不能把原筹备字段照搬，造成双方交换房间。接受方只能接受原有分配，不能借回应改变房间。

## 独立同意、真实许可与时间边界

提出和接受分别重新核验真实租约、房间控制者、各层门路、锁与实体钥匙。共同报告是已经发生的历史事实，不保证租约、钥匙和通路此后仍有效；过去报告过就绪，不能跳过本次检查。失败沿原保存点回滚，不能留下半份邀请、接受事件或其他副作用。

完整休息的最晚终点按“入住窗开始＋入住窗长度＋本人完整休息时长”计算，必须不晚于原筹备的 `required_until_at`。即使实际按整日购买的租约更长，引用该来源也不能擅自扩大当初约定的许可时段。室外会合发生在退屋后，其时间窗由原旅行的期限独立约束，不要求房租额外覆盖室外等候。

本次邀请不新建、续租或延长住房合同，不再次收费，也不授予进入伙伴房间的许可。双方接受后仍分别逐门进屋、开始自己的休息；先醒者可以独立离屋。各自完整休息、实际室外会合、共同同意恢复和真实返程，继续分别结算。

同一来源存在尚待回应、已接受、进行中或尚未结束的会合安排时，界面不会再建立另一份接续，核心仍按原分房和日程冲突门禁拒绝。来源没有永久单次消费限制：旧安排已取消，或已完成且会合等候释放后，只要仍符合原站与许可时段，可以重新明确商量新的安排。

## 界面预填、已知房间与私人信息

完成筹备后，玩家可以明确打开后续分房邀请表单。界面重新读取筹备、旅行和已有分房安排，再按当前玩家身份预填本人房间和对方房间；入住时间与本次陈述须重新填写，休息时长、时间窗和许可覆盖需要重新核对。打开表单不会提交，提交前还会重读并验证来源，避免旧界面把已变化的站点或已有新安排当作可用选择。

双方已经真实核对的两房是已知事实，分房候选可以沿用这一知识来源。当前仍可接续的来源两房优先保留，避免超过32个旧已知房间后被候选上限挤掉；总上限仍为32，不能借此枚举第三方未知住处。专项测试使用36间旧已知房、当前两房及第三方未知房，验证当前两房保留、未知房不泄漏，并且实际提出新邀请能够通过同一候选门禁。

安排记录和模型上下文保留 `source_lodging_plan_id`；紧凑共享摘要仅有来源编号、原许可终点和共同完成事件编号。分房事件也记录筹备来源及完成事件，便于追溯本次明确授权。不会把 NPC 的报价、花费、合同、私有障碍或独处活动细节混入来源摘要；伙伴自己的休息进度仍沿用阶段40的观察者知识边界。

## 存档迁移与旧回执

`journey_separate_stays.source_lodging_plan_id` 是可空外键，引用 `journey_lodging_plans`；旧库在筹备表安装后幂等追加字段和索引。历史分房记录保持空来源，不补写过去不存在的接续授权。初始化重复执行不重复加列，也不改变旧安排及活动记录。

API 沿用一份选择和原请求回执。旧分房请求没有这个新增字段、而当前字段值为 `null` 时，哈希兼容仅允许剔除该空字段，从而识别同一旧请求。非空来源不能被剔除；重试不能悄悄换来源、条款或授权。新增来源、原输入、请求编号和证据继续按已有幂等规则保存。
