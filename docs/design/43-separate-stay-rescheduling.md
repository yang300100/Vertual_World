# 已确认分房休息与会合的协商改期

阶段43为已确认、尚未开始的分房安排增加一份独立改期提议。双方可以商量新的入住开始时间；另一方明确接受之前，原分房时间、日程与个人房间继续生效。核心、文本、API 与界面已接入，44个文件876项唯一回归、真实模型全流程与28项专项审计已通过。正式服务已更新，备份、迁移、健康心跳及玩家保护的16项最终核验全部通过，见 `run/separate-stay-change-verification.json`；本次交付状态为 `verified_code_and_service`。

本次沿用用户选定的代码与服务验收范围，实际浏览器操作留待后续。界面脚本测试和真实浏览器操作分别记录。

## 只调整开始时间，保留原承诺

`SeparateStayIntent` 增加 `reschedule`、`accept_change`、`decline_change` 和 `withdraw_change`，并增加可空的 `change_id`。`reschedule` 仅引用真实 `stay_id`、新的带时区 `arrival_world_time` 与本人陈述；人、房间、订房来源、原旅行、入住窗长度、完整休息时长及会合窗长度均沿用原约定，不能借改期互换房间或扩大租期。

新开始时间须在当前世界时间之后、一个世界日以内，并与原开始时间不同。规则只在原安排已经 `accepted`、当前早于原入住窗开始、双方均未开始任何绑定休息时允许提出。入住窗已经开始后，即使一方尚未入住，本阶段也不再开放改期；已经开始的个人休息不能被新提议打断或重置。

改期提议不会替换原安排，也不先预留候选新时段。原确认时间仍约束双方的工作、出行和自主赴屋；提出改期不建立新分房记录、活动、租约或费用。等待期间双方另行接受的新日程，仍可在之后的改期接受核验中构成真实冲突。

## 独立回应与原子更新

接受或婉拒使用 `accept_change`／`decline_change`、真实 `stay_id` 与 `change_id`、本人陈述；只有本次改期的收到者可以回应。提出者可通过 `withdraw_change` 撤回自己的提议；本人撤回与旧安排的个人取消一样，不要求对方恰好可接触，但不开放远处的新邀请或代他人回应。原有 `accept`／`decline` 继续只处理初次分房邀请，不能被新增操作改变含义。

`SeparateStayChangeService` 保存原确认事件与原条款快照。接受时同时检查原安排仍是未开始的同一份确认状态、原事件与快照未变、双方仍可商量，以及当前原旅行、真实到站、停留序号和暂停回执仍一致。提出与接受都重验各自完整房间许可、每层门路与真实钥匙、当前路程和其他已确认日程。核验新日程时仅排除被改期的原安排自身，不能略过其他义务。

带阶段42订房来源的安排，其最晚完整休息终点仍不得超过原 `required_until_at`。室外会合终点继续受原旅行期限约束；没有订房来源的旧安排同样核对实际租住和钥匙，不凭改期补出接待、钥匙或续租许可。

只有全部检查通过且另一方明确接受后，才在同一保存点内更新原分房记录的五个时间字段和当前确认事件，并让 NPC 的下一次自主排程及时重新核对。原分房编号、双方身份、房间分配、原订房来源、入住窗和休息时长均保持。已在前往同一房间的真实移动不会因此被停止、替换或传送；NPC 仍自行依据新的已确认时间继续安排。

原邀请的逐字陈述和回应作为历史保留。当前时间读原分房记录已更新的时间字段，改期记录保留本次提出者、原时间、新时间及接受回应，避免用旧邀请中的日期误述当前承诺。任何写入失败沿现有分房保存点整体回滚，不能留下“改期已接受”却原时间未更新的半笔结算。

## 截止、入住与取消

一份改期的截止为原、新入住窗开始时间的较早者。到点仍未得到明确接受，改期记为 `expired`，不把未回应变成失约，也不将候选时间用于入住。婉拒或撤回仅终结改期；原安排按其自身真实状态继续处理，不自动取消、恢复或重新创建。

时钟边界纳入待回应改期的截止；一次较长的主动等候或后台推进不能跳过更早的新时间边界。原安排开始入住、被取消、状态或确认来源变化，或一方表达暂停联系时，尚待回应的改期停止。业务写操作始终重新读取当前状态，不能用旧页面的接受按钮覆盖已经开始的个人休息。

每份原安排最多有一份 `pending` 改期，由数据库唯一索引约束。旧提议婉拒、撤回或失效后，若原安排仍符合当前条件，可以另行商量；已接受过一次改期后也可再次提出，但须基于新的当前确认事件与完整原条款快照。

## 持久化、接口与知识边界

`journey_separate_stay_changes` 保存原安排、双方本次改期角色、原确认事件和条款快照、原新时间、截止、逐字陈述与回应、提议及当前来源事件、状态和原因。独立改期表避免把候选误当成第二份待执行住宿。初始化幂等安装表和索引，既有分房、活动和租约不被改写。

API 仍通过 `POST /api/worlds/{world_id}/player/social-choices` 结算唯一的玩家本人选择，并保留原输入、请求编号、逐字证据和幂等回执。新增 `change_id=null` 时兼容旧回执缺失该空字段；真实非空改期编号不能被剔除或在重试中替换。

原分房 `rows` 增加 `can_reschedule` 与 `reschedule_requests`。前者只依据双方已知的确认状态和时间展示，不通过伙伴私下是否入住、活动编号或身体原因暴露进度；最终业务授权仍重查真实状态。后者展示当前待回应提议与有限历史，只含双方已说出的改期条款和回应，文本继续按观察者姓名知识遮蔽。NPC 上下文仅固定保留当前 `pending` 改期的紧凑条款，旧已终结历史不挤占本轮必须输入。

场景与人物档案提供明确的新时间表单，以及接受、婉拒和本人撤回操作。界面核对当前来源和待回应状态，变更过程中禁用重复操作，旧世界、旧人物或在途回包不能向新页面提交。模型仍只提出本人的结构化意愿，台词中的“可以”不会被规则补成改期接受。
