# 世界元素生命周期与现场拍照

状态：已实现（2026-08-31）。

## 评估结论

“整个世界的数据都视为元素”是合理且有利的方向，但不能把人物、地点、建筑、记忆、物品等
全部塞进一张任意 JSON 表。那会丢掉血缘、资源扣除、空间范围、生命值、建设状态等数据库约束，
也会让规则引擎难以验证。

本项目采用混合的面向对象式模型：

```text
WorldElementCatalog                    统一基类式目录
├── identity: entity_type + entity_id
├── lifecycle: active / destroyed / retired
├── provenance: seed / system / registration + 来源事件
└── metadata: 仅放跨领域的小型索引数据

characters / locations / buildings / world_structures / ...   各自的专用子类事实表
├── 人物：生命、坐标、状态、谱系
├── 地点：范围、资源、父级地点、是否可用
├── 建筑/遗迹：类型、位置、施工或损毁状态
└── 知识：可见性、置信度、退役状态
```

因此，统一目录回答“它是什么、来自哪里、是否仍存在”；专用表回答“它有哪些属性、允许哪些
方法/状态迁移”。新增元素类型只需增加专用表和受限处理器，再登记到目录；不会破坏旧存档。

## 删除器

`WorldElementRemover` 是注册器的对偶入口：每次请求必须带来源事件、事件参与者、目标元素、
原因和幂等键。它不会执行物理 `DELETE`，而是写入删除请求、效果记录、`world.element_removed`
事件与元素墓碑。

- 建筑、遗迹：改为 `ruined`；未完工项目以“毁灭”结束，不伪造退款。
- 地点/聚落：变为不可用；仍有活着的人物在场时拒绝，要求先通过事件完成撤离。
- NPC：生命归零、退出活跃状态；玩家仍走专用的败北/复苏流程。
- 知识：变为 `retired`；载具：变为不可用。

物理行不会删除，因而不破坏事件、谱系、注册和照片的外键引用。已结算战斗令 NPC 死亡时，
引擎会自动调用该删除器；其他可毁元素可由后续动作处理器或 API 使用同一契约接入。

## 现场拍照

拍照不是仅把“画一张图”交给模型。`PhotoService` 在调用模型前固定并留档：

1. 玩家精确坐标、当前地点与镜头东南西北朝向；
2. 伊瑟拉历季节、昼夜时段与对应光照；
3. 已审核导航数据集中的地貌、生物群系、地表类型、海拔、坡度、河流/道路/渡口；
4. 该朝向 12 公里扇形内的已登记建筑、遗迹和地图特征；
5. 1.5 公里或同地点内的真实在场人物；
6. 用户选择的自拍、附近 NPC、指定 NPC 与上传的人设参考图。

这些内容会被写成提示词及 `photo_captures.context_json`。生成请求在数据库读快照完成后、
写事务之外执行，只有最终图片、事件和审计记录会使用短写事务。最终图片保存到本地
`WORLD_MEDIA_DIR/<world_id>/photos/<capture_id>.<ext>`，人设图保存到
`WORLD_MEDIA_DIR/<world_id>/portraits/<character_id>/`。图片服务可由 `.env` 配置，默认按 Seedream 兼容的
`/images/generations` 协议请求；模型名默认为哥哥指定的 `seedream5.0lite`。

人设图只接受 PNG/JPEG/WebP data URL，服务端检查格式签名和 8MiB 上限，使用哈希生成文件名，
不接受客户端给出的路径。生成图片同样落在本地媒体目录后才以 `/world-media/` 提供。
